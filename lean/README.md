# Lean 4 certificate for the degree-3 relevant-variables problem

A Lake project on **Lean 4.23.0** with **Mathlib pinned at tag `v4.23.0`**, commit
`37df177aaa770670452312393d4e84aaad56e7b6`. Zero `sorry`, no `native_decide`, standard axioms only.

## Building

```bash
cd lean
lake exe cache get     # fetches Mathlib and its olean cache (needs network; several GB)
lake build
bash gate.sh           # writes GATE.txt and AXIOMS.txt; exits 0 only on a clean run
```

`lake-manifest.json` was written by hand from the manifest of the local Mathlib checkout the project
was developed against, with the Mathlib entry changed from a local `path` dependency to the pinned
git revision above; the inherited dependency revisions (batteries, aesop, Qq, proofwidgets,
importGraph, LeanSearchClient, plausible, Cli) are Mathlib `v4.23.0`'s own. It was not regenerated by
a fresh `lake update`, because that would have forced a full Mathlib rebuild. If `lake` complains
about the manifest, `lake update` will rewrite it; the toolchain and the Mathlib revision are the
things that must not change.

## What is proved

Everything is stated about an arbitrary solution `IsSol n N` of the **frozen** finite statement in
`R3/Statement.lean`, which transcribes `../proofs/FINITE_STATEMENT.md`. That file must not be edited:
it is what makes the certificate mean something.

| file | content |
|---|---|
| `R3/Statement.lean` | FROZEN: `card`, `IsCoeffVec`, `CondI`, `CondII`, `CondIII`, `IsSol`, `F n` |
| `R3/Basic.lean` | `chi`, `evalF`, `evalF_sq` (`f_N^2 = 16`), `linkVal_mem` (E1), `two_dvd_mass`, `four_le_mass` (E2), `sum_mass_le`, `mass_four_pm`, `mass_four_card`, `mass_four` |
| `R3/Mass.lean` | `mass_le_eight`, `mass_cases` (`n >= 11`: mass ∈ {4,6,8}, Lemma 1), `card_mass_ne_four_le_two`, `nine_mass_four` (`n = 11`: ≥ 9 vertices of mass 4), `exists_mass_four`, `bookkeeping` (`e + delta = 48 - 4n`) |
| `R3/Link.lean` | `card_xor_two_pow`, `mass_four_link` (Lemma 2(a): four distinct link sets of size ≤ 2, xor 0, coefficients ±1 with product 1), `mass_four_even_degree` |
| `R3/Twelve.lean` | `twelve_mass_four`, `twelve_card_three` (`n = 12`: all masses 4, all terms cubic — Step 1), `twelve_coeff_pm`, `twelve_link_card_two`, `twelve_link` |
| `R3/Cycle.lean` | `exists_pair_of_card_two`, `four_pairs_cycle`, `twelve_link_cycle` (`n = 12`: every vertex link is a 4-cycle — Step 2) |

Top certified theorem: `R3.twelve_link_cycle`. All 23 gated declarations report
`[propext, Classical.choice, Quot.sound]`; the verbatim output is `AXIOMS.txt` and the dated gate run
is `GATE.txt`.

## What is not proved

`F(12)` and `F(11)` themselves. Steps 3 and 4 towards `F(12)` (closure of the 4-cycle links to two
vertex-disjoint octahedra, then the contradiction from `CondII` at `U = S ∪ T`) are **in progress**;
`PLAN.md` gives the route, the next lemma and the effort estimates, and `HANDOFF.md` the current
state. `R3/Octahedron.lean` and `R3/WIP.lean` hold that in-progress work: they are **not** imported by
`R3.lean`, so `lake build` does not build them and the gate does not cover them. Do not read a claim
into them.

Also not formalised: the reduction from degree-3 Boolean functions to `F(n)` (the `2^{1-d}`
granularity of the Fourier coefficients), which is the bridge between `F(11)` and `R_3 <= 10`; and the
general-`d` theorem that the Nisan–Szegedy bound is never tight.

`TOOLCHAIN_NOTES.md` records the toolchain and build environment details.
